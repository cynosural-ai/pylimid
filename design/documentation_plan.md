## Site structure

The site order is **Getting started → User guide → Tutorials → API reference**. There is no separate Background section (see [Theory and references](#theory-and-references)).

Each section answers a different question, and content belongs to the section whose question it answers:

- **Quickstart**: "show me it working". One problem, the whole workflow (build, validate, draw, solve), a few minutes to read.
- **Tutorials**: "show me a real problem". Story-driven, one model end to end, with figures and interpretation of the result. They teach by example and do not list every option.
- **User guide**: "how do I do X, and what happens when Y". One concept per page: every option, edge cases, errors, short synthetic snippets, and links out to tutorials for complete examples.
- **API reference**: "what exactly does this function take". Generated from docstrings.

There is **no published developer guide**. Contributor documentation lives in `CONTRIBUTING.md`, `AGENTS.md`, and `design/` (ADRs and living design notes), which stay out of the published site. The only architecture content that belongs in `docs/` is a short user-facing explanation of how a diagram becomes a NumPyro model and which engine runs when, because users need it to trust the results.

### Where PyLIMID adds value over NumPyro

The docs should not re-explain NumPyro: link to its documentation for distributions and MCMC. Spend the words on what no other documentation covers:

- information sets and memory: what a decision observes, why memory arcs are explicit in a LIMID, and the rule that decisions only observe discrete parents;
- policies and solving: what a policy is, which solver runs when, what solvability means, and how to read and trust Monte Carlo results (`num_samples`, `rng_key`, failure modes);
- how the NumPyro pieces plug in: what a `dist` or `values` callable receives, and why it must be written in JAX;
- modelling patterns specific to decision problems: binning a continuous score into a discrete report, several additive utilities, risk preferences, priors on parameters, value of information.

## Theory and references

Theory goes inline in the user guide page where it explains a behaviour the reader will meet, with a citation instead of a derivation. No math-heavy pages, and nothing a textbook explains better. Planned inline theory:

- Decisions and information sets: why LIMIDs drop no-forgetting, which is why memory arcs must be drawn (Lauritzen and Nilsson, 2001).
- Solving: what solvability means and why backward induction needs it (Lauritzen and Nilsson, 2001); why results are Monte Carlo estimates (Bielza et al., 1999).
- Utilities: expected utility and risk attitude, why a concave utility changes the decision (Clemen).

**The solvability note is original content and must be kept.** The library's solvability check follows Lauritzen and Nilsson (2001) exactly and is stricter than pyAgrum's `isSolvable()`: in the `D1 → X → D2` case documented in `design/inference/solver_algorithms.md`, pyAgrum reports an expected utility of 4.0 while the optimum is 5.0. It goes in the Solving page as a section or a collapsible note.

**Further reading page**, grouped by topic with one line on what each source is good for:

- Getting started with decision analysis: the blog series ([I](https://ferjorosa.github.io/blog/2025/06/08/decision-theory-I.html), [II](https://ferjorosa.github.io/blog/2025/07/04/decision-theory-II.html), [III](https://ferjorosa.github.io/blog/2025/08/07/decision-theory-III.html)) and Clemen, *Making Hard Decisions*.
- Influence diagrams and LIMIDs: Kjærulff and Madsen; Koller and Friedman, chapters 22–23; Lauritzen and Nilsson (2001).
- Monte Carlo decision analysis: Bielza et al. (1999); Charnes and Shenoy (2004).
- The tools underneath: NumPyro's documentation; pyAgrum for exact discrete solving.

Plain links and author–year citations are enough for now; `sphinxcontrib-bibtex` can wait until there are many citations. The full candidate list is under [References](#references); verify each entry before publishing.

## Writing style

These conventions came out of reviewing the home, installation and quickstart pages. Follow them in every page and in `README.md`.

**Voice**

- Write for a reader who is new to the library: complete sentences, a story or concrete problem before the code, and every term explained the first time it appears.
- Prefer plain words over jargon ("draws values from each distribution" rather than "traces the sites"). No arrow chains, no undefined shorthand.
- Keep pages short by choosing what to include, not by compressing sentences.
- Do not break lines at 80 characters (see `AGENTS.md`).

**Names and terms**

- In prose, write **PyLIMID**. Use `pylimid` only for the package name: imports, `pip install`, extras, URLs.
- **Node** is an element of the diagram (chance node, decision node, utility node) and the word to use when talking about structure or the API. **Variable** is the value a chance or decision node represents, and the word to use when talking about discrete or continuous values and inference.
- Say chance nodes can be "discrete, continuous, or both in the same model". A single variable is not "mixed"; the diagram is.

**Accuracy: do not overpromise**

- Distributions and utilities must be JAX-traceable: pure `jnp` expressions, no `float()` / `int()` coercion, no Python `if` on a parent value (use `jnp.where`). Never describe them as "arbitrary code" or "any function".
- Decisions choose among a finite set of actions, and they can only observe discrete parents. State this wherever decisions are introduced.
- Inference: discrete variables are handled by exact enumeration and continuous ones by MCMC (NUTS). In a mixed diagram the discrete posterior is still an estimate, so tie "exact" to the method, not to the result.
- Results of `infer` and `solve` are Monte Carlo estimates. A run is reproducible for a fixed `rng_key` (default seed 0).
- `infer(..., policy=...)` clamps each decision to one action in every case; it is for "what if we always did X" questions. Do not tell readers to pass `solve()`'s policy to `infer()`: that policy is state-dependent and `infer` does not evaluate it.
- Performance claims stay modest: "efficiently on CPU and GPU", not "fast". For pyAgrum, "may be a better choice" or "is the better choice for purely discrete diagrams", without disparaging it.

**Numbers and examples**

- Every number quoted in prose must come from running the page's code. Re-run and re-check the prose whenever the model changes.
- When a decision chooses from a menu of actions, check that the optimum is not the largest (or smallest) option, otherwise the solver only returns the menu's edge. The quickstart's sunny-day answer (200) sits at the top of its 0–200 menu; it is genuinely optimal (the exact optimum is about 200.4), but any change to the numbers must re-check this.
- Pages show only code that teaches PyLIMID. Plotting code does not go in the page: generate the figure with a script, commit the script next to the image, and embed the image with a `{figure}` directive.

**Installation and GPU**

- Recommend the `cuda12` and `cuda13` extras. Do not mention the `gpu` extra in the docs; it still exists in `pyproject.toml`, but it is deliberately not advertised.

**Links**

- Inside `docs/`, use relative links to other pages.
- In `README.md`, link to the Read the Docs pages, not to `.md` sources: GitHub does not execute the `{code-cell}` blocks, so the sources show code without outputs.

## Files, figures and drafts

- Figures live in `docs/_static/figures/<page>/`. When a figure is generated, the script that generates it sits in the same folder (for example `docs/_static/figures/quickstart/plot_demand.py`, run from the repository root with `uv run python docs/_static/figures/quickstart/plot_demand.py`). The script's numbers are copied from the page, so change both together.
- Drafts that should not be published go in a folder listed in `exclude_patterns` in `docs/conf.py`. Today that is `docs/quickstart/`, which holds `bayesian_priors.md`, the plan for extending the quickstart with a Bayesian prior. A Markdown file in `docs/` that is neither in a toctree nor excluded makes the `-W` build fail.
- `docs/conf.py` sets `JAX_PLATFORMS=cpu` and a `PYTHONWARNINGS` filter for tqdm's "IProgress not found" warning, so executed cells stay free of environment noise.
- Build with `uv run sphinx-build -W docs docs/_build/html`. `nb_execution_mode = "cache"` re-runs only pages whose code changed; a clean build re-runs every page and takes several minutes because of the tutorials.

## Publishing

- Read the Docs builds the `latest` version from `main` on every push, and the site's root redirects to `latest`. Docs-only changes therefore need no release.
- The `stable` version (newest tag) appears not to be activated. It only matters if the default version is switched to `stable`.
- The PyPI project page shows the README of the last released package, so README changes reach PyPI only with the next release. Releases are made by pushing a `v*` tag (version from git tags through `hatch-vcs`); `.github/workflows/release.yml` builds, publishes to PyPI and creates the GitHub release.

## Earlier decisions still in force

Kept from the first iteration of this plan, condensed.

**Public API.** The public surface was settled before generating the API reference, because published import paths are commitments:

- `pylimid.solve(diagram, method="auto" | "backward_induction" | "scan", num_samples=2000, rng_key=None)` is the single front door for solving. `"auto"` runs backward induction when the diagram is solvable and the batched scan otherwise. `Solution.method` records which solver ran (`"backward_induction"` or `"scan"`, never `"auto"`).
- `pylimid` re-exports the node types, `InfluenceDiagram`, `infer`, `solve`, `Solution`, `Posterior`, `Policy`, `InferenceResult`, `InferenceError`, `SolveMethod` and `SolverName`. `Snapshot`, `Node`, `NodeKind`, `Consistency`, `DiagramProblem` and `ProblemKind` stay in `pylimid.graph`; `is_solvable` and `solvability_order` stay in `pylimid.inference.numpyro.solvers`.
- Docstrings follow the Google convention, with single backticks for cross-references to public names and double backticks for literal code. `docs/conf.py` has a `missing-reference` hook that resolves a bare name when exactly one documented object matches it.

**Tooling.** Sphinx with `myst-parser` and `myst-nb` (Markdown pages, `{code-cell}` blocks executed in a Jupyter kernel and cached), `autodoc` + `napoleon` + `autosummary` for the API reference, `sphinx-copybutton` and `sphinx-design` (home-page cards), the Read the Docs theme, Graphviz for diagram SVGs (`_repr_svg_`), Mermaid kept for text output.

**Positioning against pyAgrum.** Be honest about when to use something else: for purely discrete diagrams that need exact answers, pyAgrum is the better tool, and the test suite uses it as the reference for `infer` and `solve`. PyLIMID is for models with continuous or mixed uncertainty, distributions beyond tables, and utilities that are functions.
