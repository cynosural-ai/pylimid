# Documentation plan

The working document for the published documentation site (`docs/`, built with Sphinx and hosted on [Read the Docs](https://pylimid.readthedocs.io)). It records where the docs stand, the decisions taken so far, and the conventions every page follows. Read it before changing anything in `docs/` or `README.md`, and update it when a decision changes.

Inspiration: [NumPyro](https://num.pyro.ai/en/stable/) for the layout and [pyAgrum](https://pyagrum.readthedocs.io) for notebooks-as-documentation.

## Site structure

The published site order is currently **Getting started → User guide → Resources → API reference**. Tutorials are planned between User guide and Resources, but their home-page card, toctree and links from the quickstart and README are commented out until the pages are reviewed. Their sources remain in `docs/tutorials/`, excluded from the build. Resources currently contains Common pitfalls; background material and references can be added later.

Each section answers a different question, and content belongs to the section whose question it answers:

- **Quickstart**: "show me it working". One problem, the whole workflow (build, validate, draw, solve), a few minutes to read.
- **Tutorials**: "show me a real problem". Story-driven, one model end to end, with figures and interpretation of the result. They teach by example and do not list every option.
- **User guide**: "how do I do X, and what happens when Y". One topic per page, following the ice cream shop so readers only learn the problem once. Explain concepts where they are used, with small model variants and the errors users are likely to meet. The last page extends the shop to two decisions. Tutorials provide complete alternative problems.
- **Resources**: "what should I check when something behaves unexpectedly". Common pitfalls collects short, standalone examples. Background and references may follow when there is material worth publishing.
- **API reference**: "what exactly does this function take". Generated from docstrings.

There is **no published developer guide**. Contributor documentation lives in `CONTRIBUTING.md`, `AGENTS.md`, and `design/` (ADRs and living design notes), which stay out of the published site. The only architecture content that belongs in `docs/` is a short user-facing explanation of how a diagram becomes a NumPyro model and which engine runs when, because users need it to trust the results.

### Where PyLIMID adds value over NumPyro

The docs should not re-explain NumPyro: link to its documentation for distributions and MCMC. Spend the words on what no other documentation covers:

- information sets and memory: what a decision observes, why memory arcs are explicit in a LIMID, and the rule that decisions only observe discrete parents;
- policies and solving: what a policy is, which solver runs when, what solvability means, and how to read and trust Monte Carlo results (`num_samples`, `rng_key`, failure modes);
- how the NumPyro pieces plug in: what a `dist` or `values` callable receives, and why it must be written in JAX;
- modelling patterns specific to decision problems: binning a continuous score into a discrete report, several additive utilities, risk preferences, priors on parameters, value of information.

## User guide

The user guide has five core pages. The first four follow the single-order ice cream shop; the fifth extends it to two decisions. There is no separate Core concepts section: explanations live beside the model behaviour they describe. A reading list is optional rather than another core guide.

The ice cream example in Building a diagram, Solving a diagram and Inference uses bookings at nearby hotels (`bookings`, states `normal` and `high`) as an additional influence on demand. The owner initially has no access to current booking figures before ordering, so only weather is a parent of `order`. The probabilities (`5 / 7`, `2 / 7`) represent estimated historical proportions, with demand multipliers (`1.0`, `1.5`). The inference subsection introduces a free report that accurately identifies the booking state, adds `bookings` to the decision's parents, solves again, and infers profit given sunny weather and high bookings. No report node or purchase decision is needed for this simplified example.

2. **Distributions and utilities**: what chance and utility functions receive from their parents; discrete state indices; Gamma demand and a truncated Gaussian alternative; additive revenue and cost utilities; JAX expressions, with table-indexing and parent-effect checks linked from Resources. Keep the first two sections focused on functions and distributions, with separate small code cells for `demand_dist` and `profit`, and categorical functions for weather and hotel bookings. Introduce the Gaussian alternative directly through `TruncatedNormal`, explaining that demand cannot be negative and that truncation changes the actual mean. Compare the Gamma and truncated Gaussian density curves for sunny weather and normal hotel bookings in a static figure, with its generating script beside the image. Do not construct, draw, validate or solve a diagram in these opening sections. The payoff-splitting section constructs and displays the complete Gamma diagram in one cell, reusing the functions introduced earlier. A separate cell copies the diagram, replaces `profit` with `revenue` and `cost`, and displays the split version before comparing the solutions. Briefly explain continuous demand as an approximation to a count and the role of Gamma concentration in setting its spread. Keep the utility comparison output to policy equality and expected profits. The JAX section explains its main requirements through an intentionally incorrect utility function, with inline replacements for casts, Python min and a parent-dependent if. Keep this example in a non-executed Python block and link to JAX’s Just-in-time compilation guide in an info box. Link to the standalone Common pitfalls page for table indexing and checking parent effects. Keep hotel bookings and the 0–200 order menu. Bayesian priors and fitting remain future topics.
3. **Solving**: kept, plus the user-facing "how it works" explanation and the solvability note against pyAgrum (see below).
4. **Inference**: rebuild the shared ice cream diagram in the introduction so each question section can focus on the calls that answer it. First show the distribution of daily profit behind the recommended policy's expected utility. A short subsection then considers a sunny day with a free hotel report revealing high bookings before ordering. Assume the report identifies the booking state accurately. Copy the diagram, add `bookings` as a parent of `order`, and solve again so the policy uses both variables. Then infer the profit distribution with both observations, introducing `observed` and discrete state indices. Keep this subsection focused on the new information, the updated policy and the conditional distribution. Keep the original diagram and policy available for the following comparisons. Then compare the original weather-based policy with ordering 160 every day, showing both distributions and estimated expected profits. Introduce event probabilities through stockout risk in the final demand section, without a separate loss-probability section. Make the final section broaden the scope to other model variables, using a delivery shortfall as motivation for showing the conditional demand distribution and querying demand above 150 on a sunny day. Reuse the observation syntax and explain why a demand query needs no order policy. The first three section titles match the opening questions, in the same order; the demand question extends the story afterwards. All sections are drafted in [the inference guide](../docs/user_guide/inference.md), with profit distributions, a policy comparison and the conditional demand histogram. Review the full flow with the three opening questions: profit under the recommended policy, an alternative policy and demand exceeding available stock. The draft is included in the documentation build for review. Distinguish expected utility (the mean) from the distribution of utility across days. Explain results and sampling reliability where they are used, without a separate closing section after the demand question. Keep parameter learning and fitting on a separate future page.
5. **Multiple decisions**: extend the shop with a promotion booked before the weather is known, followed by the stock order. The promotion affects demand and has a separate cost utility. Bookings remain unknown at both decisions; `order` observes only `weather` and the earlier `promotion` choice. Follow this flow: add the promotion, solve and read both policies, remove the memory arc and explain its effect on solvability, then explore the outcomes with both policies using `infer`. ## Resources

Resources is a sidebar heading with Common pitfalls directly underneath, without a separate landing page. The page lives at `docs/resources/common_pitfalls.md` and is a general reference for surprising behaviour across PyLIMID. Add or remove entries as they become relevant or obsolete, including removing workarounds when upstream bugs are fixed. Each pitfall has its own visible section and executable code cell, with enough context and imports to be understood independently of the user guide or other examples. The two current entries cover indexing a demand table with both discrete parents in one operation (NumPyro issue #2252) and detecting a missing lookup-table value with `probe_discrete_parents()`. Lead each entry with the problem and how to avoid or detect it, followed by a short code example. Keep background to the minimum needed to understand the issue, following the user guide’s writing style.

## Theory and references

Theory goes inline in the user guide page where it explains a behaviour the reader will meet, with a citation instead of a derivation. No math-heavy pages, and nothing a textbook explains better. Planned inline theory:

- Multiple decisions: why LIMIDs drop no-forgetting, which is why memory arcs must be drawn (Lauritzen and Nilsson, 2001).
- Solving: what solvability means and why backward induction needs it (Lauritzen and Nilsson, 2001); why results are Monte Carlo estimates (Bielza et al., 1999).
- Utilities: expected utility and risk attitude, why a concave utility changes the decision (Clemen).

**The solvability note is original content and must be kept.** The library's solvability check follows Lauritzen and Nilsson (2001) exactly and is stricter than pyAgrum's `isSolvable()`: in the `D1 → X → D2` case documented in [the solver design](solver/algorithms.md), pyAgrum reports an expected utility of 4.0 while the optimum is 5.0. It goes in the Solving page as a section or a collapsible note.

**Further reading page**, grouped by topic with one line on what each source is good for:

- Getting started with decision analysis: the blog series ([I](https://ferjorosa.github.io/blog/2025/06/08/decision-theory-I.html), [II](https://ferjorosa.github.io/blog/2025/07/04/decision-theory-II.html), [III](https://ferjorosa.github.io/blog/2025/08/07/decision-theory-III.html)) and Clemen, *Making Hard Decisions*.
- Influence diagrams and LIMIDs: Kjærulff and Madsen; Koller and Friedman, chapters 22–23; Lauritzen and Nilsson (2001).
- Monte Carlo decision analysis: Bielza et al. (1999); Charnes and Shenoy (2004).
- The tools underneath: NumPyro's documentation; pyAgrum for exact discrete solving.

Plain links and author–year citations are enough for now; `sphinxcontrib-bibtex` can wait until there are many citations. The full candidate list is under [References](#references); verify each entry before publishing.

## Writing style

These conventions came out of reviewing the home, installation and quickstart pages. Follow them in every page and in `README.md`.

**Voice**

- Write for a reader who is new to the library: complete sentences, a story or concrete problem before the code, and every term explained the first time it appears.
- Avoid pronouns for the ice cream shop owner, including singular "they". Rephrase sentences naturally or use "the owner" where needed, without specifying gender.
- Use "we" for the author and reader working with PyLIMID: building the model, calling functions and interpreting results. Use "the owner" or "the shop" for decisions and information in the example. Introduce scenarios directly ("Suppose today is sunny") rather than putting the reader in the owner's role.
- Use present tense for walkthrough steps and API behaviour. Past and present perfect refer to earlier steps; conditionals describe hypothetical alternatives.
- Prefer active voice when the actor helps explain the action: "we add", "PyLIMID checks", "the owner chooses". Keep passive voice when the actor is unimportant, such as when describing what is known or how a distribution is parameterised.
- Prefer plain words over jargon ("draws values from each distribution" rather than "traces the sites"). No arrow chains, no undefined shorthand.
- Keep pages short by choosing what to include, not by compressing sentences.
- Keep explanations and output only when they help the reader understand the example. Put reusable debugging examples on the Common pitfalls page and link to them where relevant.
- Do not break lines at 80 characters (see `AGENTS.md`).

**Names and terms**

- In prose, write **PyLIMID**. Use `pylimid` only for the package name: imports, `pip install`, extras, URLs.
- **Node** is an element of the diagram (chance node, decision node, utility node) and the word to use when talking about structure or the API. **Variable** is the value a chance or decision node represents, and the word to use when talking about discrete or continuous values and inference.
- Use code formatting for specific node names and Python identifiers ("the `profit` node", "the `profit` function", "the `order` node's `states`") and literal state labels when explaining their encoding. Keep ordinary concepts in plain text ("expected profit", "high demand", "sunny weather").
- Say chance nodes can be "discrete, continuous, or both in the same model". A single variable is not "mixed"; the diagram is.

**Accuracy: do not overpromise**

- Chance nodes with `states` require Categorical with one label per category or Bernoulli with exactly two labels, for either probabilities or logits and including zero-probability outcomes. Nodes with `states=None` require continuous support; count distributions are unsupported. Keep the distributions guide focused on supported distributions and label requirements. Document the full contract and its validation timing in `ChanceNode`. Execution docstrings should retain relevant exception descriptions without repeating the contract.
- Distributions and utilities must be JAX-traceable: pure `jnp` expressions, no `float()` / `int()` coercion, no Python `if` on a parent value (use `jnp.where`). Never describe them as "arbitrary code" or "any function".
- Decisions choose among a finite set of actions, and they can only observe discrete parents. State this wherever decisions are introduced.
- Inference: discrete variables are handled by exact enumeration and continuous ones by MCMC (NUTS). In a mixed diagram the discrete posterior is still an estimate, so tie "exact" to the method, not to the result.
- Results of `infer` and `solve` are Monte Carlo estimates. A run is reproducible for a fixed `rng_key` (default seed 0).
- `infer(..., policy=...)` accepts fixed actions for "what if we always did X" questions and the state-dependent policy returned by `solve()`.
- Performance claims stay modest: "efficiently on CPU and GPU", not "fast". For pyAgrum, "may be a better choice" or "is the better choice for purely discrete diagrams", without disparaging it.

**Numbers and examples**

- Every number quoted in prose must come from running the page's code. Re-run and re-check the prose whenever the model changes.
- When a decision chooses from a menu of actions, check that the optimum is not the largest (or smallest) option, otherwise the solver only returns the menu's edge. The quickstart's sunny-day answer (200) sits at the top of its 0–200 menu; it is genuinely optimal (the exact optimum is about 200.4), but any change to the numbers must re-check this.
- Pages show only code that teaches PyLIMID. Plotting code does not go in the page: generate the figure with a script, commit the script next to the image, and embed the image with a `{figure}` directive.

**Installation and GPU**

- Recommend the `cuda12` and `cuda13` extras. Do not mention the `gpu` extra in the docs; it still exists in `pyproject.toml`, but it is deliberately not advertised.

**Links**

- Inside `docs/`, use relative links to other pages.
- In `README.md`, link to the Read the Docs pages, not to `.md` sources: GitHub does not execute the `{code-cell}` blocks, so the sources show code without outputs.
- Link API names in prose to the API reference with MyST roles: ``{py:class}`InfluenceDiagram` ``, ``{py:meth}`~InfluenceDiagram.validate` `` (the `~` shows only the short name, and Sphinx adds the parentheses), ``{py:func}`solve` ``, ``{py:attr}`~Node.consistency` ``. Plain backticks in a `.md` page render as code without a link.
- Link the first mention of each name in a section, not every mention. Do not link inside headings or code cells.
- External names (Python, JAX, NumPyro) resolve through `intersphinx_mapping` in `docs/conf.py`, for example ``{py:class}`numpyro.distributions.Gamma` ``.
- `nitpicky = True` is on, so any reference that does not resolve, in a page or in a docstring, fails the `-W` build. In docstrings, refer to modules and objects that are not in the API reference with double backticks (``` ``pylimid.graph.render.mermaid`` ```), not single ones. Every public name that appears in a signature or docstring must be exported and listed in `docs/api/`, rather than silenced with `nitpick_ignore`.
- Incremental builds only re-check changed pages, so check links with a fresh build: `uv run sphinx-build -W -E docs /tmp/pylimid-docs`.

## Files, figures and drafts

- Figures live in `docs/_static/figures/<page>/`. When a figure is generated, the script that generates it sits in the same folder (for example `docs/_static/figures/quickstart/plot_demand.py`, run from the repository root with `uv run python docs/_static/figures/quickstart/plot_demand.py`). The script's numbers are copied from the page, so change both together.
- Drafts that should not be published go in a folder listed in `exclude_patterns` in `docs/conf.py`. Today those include `docs/quickstart/`, which holds `bayesian_priors.md`, and the unreviewed `docs/tutorials/`. A Markdown file in `docs/` that is neither in a toctree nor excluded makes the `-W` build fail.
- `docs/conf.py` sets `JAX_PLATFORMS=cpu` and a `PYTHONWARNINGS` filter for tqdm's "IProgress not found" warning, so executed cells stay free of environment noise.
- Build with `uv run sphinx-build -W docs docs/_build/html`. `nb_execution_mode = "cache"` re-runs only pages whose code changed; a clean build re-runs every included page. Tutorials remain excluded until reviewed.

## Visual identity

The logo uses the approved Flush mark: a pale blue rounded square, a centered circular opening and a white utility diamond whose right tip aligns with the square's edge. The wordmark is **PyLIMID**, set in Jost. The palette follows Cynosural: midnight blue ``#0A1F3D``, pale blue ``#A9C6E2`` and white. Lettering is converted to paths, so the SVGs do not need an installed font or an external resource.

The assets live in `docs/_static/branding/`. `pylimid-readthedocs.svg` is a compact transparent horizontal logo for the sidebar above the navigation; `docs/conf.py` sets `html_logo`, hides the duplicate project text with `logo_only` and uses the matching navy header background. `pylimid-readme.svg` is a wider logo on a navy background, so the README displays the same colors in GitHub's light and dark themes. SVGs are the display sources.

## Publishing

- Read the Docs builds the `latest` version from `main` on every push, and the site's root redirects to `latest`. Docs-only changes therefore need no release.
- The `stable` version (newest tag) appears not to be activated. It only matters if the default version is switched to `stable`.
- The PyPI project page shows the README of the last released package, so README changes reach PyPI only with the next release. Releases are made by pushing a `v*` tag (version from git tags through `hatch-vcs`); `.github/workflows/release.yml` builds, publishes to PyPI and creates the GitHub release.

## Earlier decisions still in force

Kept from the first iteration of this plan, condensed.

**Public API.** The public surface was settled before generating the API reference, because published import paths are commitments:

- `pylimid.solve(diagram, method="auto" | "backward_induction" | "scan", num_samples=2000, rng_key=None)` is the single front door for solving. `"auto"` runs backward induction when the diagram is solvable and the batched scan otherwise. `Solution.method` records which solver ran (`"backward_induction"` or `"scan"`, never `"auto"`).
- `pylimid` re-exports the node types, `InfluenceDiagram`, `infer`, `solve`, `Solution`, `Posterior`, `Policy`, `InferenceResult`, `InferenceError`, `SolveMethod` and `SolverName`. `DiagramSnapshot`, `Node`, `NodeKind`, `Consistency`, `DiagramProblem` and `DiagramProblemKind` stay in `pylimid.graph`; `is_solvable` and `solvability_order` live in `pylimid.solver`.
- Posterior queries and `Posterior` live in `pylimid.inference`; solver selection, algorithms and `Solution` live in `pylimid.solver`. NumPyro translation and sampling live in `pylimid.numpyro`. Shared policy representation and errors live in `pylimid.policy` and `pylimid.errors`. The package root remains the main import surface for users.
- The scan implementations and their candidate-policy enumeration helpers live in `pylimid.solver.scan`. Backward induction and structural solvability checks remain directly under `pylimid.solver`.
- `Posterior.values` and all numerical summaries use JAX arrays. Draws retain the sampler's dtype and have shape `(num_samples, *node_shape)`; summaries retain the node's shape, including zero-dimensional arrays for scalar nodes. Examples use `.item()` when they need a Python scalar for display and `.tolist()` when they need a Python list. Constructing a `Posterior` manually requires a JAX array.
- Docstrings follow the Google convention, with single backticks for cross-references to public names and double backticks for literal code. `docs/conf.py` has a `missing-reference` hook that resolves a bare name when exactly one documented object matches it.

**Tooling.** Sphinx with `myst-parser` and `myst-nb` (Markdown pages, `{code-cell}` blocks executed in a Jupyter kernel and cached), `autodoc` + `napoleon` + `autosummary` for the API reference, `sphinx-copybutton` and `sphinx-design` (home-page cards), the Read the Docs theme, Graphviz for diagram SVGs (`_repr_svg_`), Mermaid kept for text output.

**Positioning against pyAgrum.** Be honest about when to use something else: for purely discrete diagrams that need exact answers, pyAgrum is the better tool, and the test suite uses it as the reference for `infer` and `solve`. PyLIMID is for models with continuous or mixed uncertainty, distributions beyond tables, and utilities that are functions.
